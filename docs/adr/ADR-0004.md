# ADR-0004 — asyncpg as the single PostgreSQL driver

- **Status:** Accepted — **revised 2026-10-13** (post-Phase-0 cleanup). Supersedes the original
  Phase 0 decision to use psycopg 3, retained below as history.
- **Phase:** 0 / 0.5

## Context

SQLAlchemy needs a PostgreSQL driver for the async application (FastAPI, the worker) and for Alembic.
Phase 0 chose psycopg 3. Its three packages — `psycopg`, `psycopg-binary` and `psycopg-pool` — are
licensed **LGPL-3.0-only**, which was flagged for the user's confirmation.

The user decided against it: **the product may later be distributed as an Electron desktop
application** (ADR-0008). LGPL obligations attach to distribution. A self-hosted server never
distributes its dependencies; a desktop installer does. The user prefers an Apache-2.0 driver.

## Decision

**`asyncpg==0.31.0`** (Apache-2.0) is the **only** PostgreSQL driver, through one URL scheme:
`postgresql+asyncpg://`.

- `Settings` rejects every other scheme at startup (`ken_core/config.py`, `_require_asyncpg_driver`),
  including the previous `postgresql+psycopg://`. The error never echoes the URL (no credentials).
- SQLAlchemy remains the database abstraction; only the dialect changed. The application already used
  only `AsyncEngine`/`AsyncSession`, so no application query code changed.
- Alembic already ran its migrations through an **async** `env.py` (`create_async_engine` +
  `run_sync`), so it works with asyncpg unchanged apart from the URL scheme.

### Why 0.31.0 and not the newest release

0.32.0 was released on 2026-10-06, seven days before this decision. 0.31.0 (November 2025) has close
to a year of production use, and both ship `cp312` wheels for macOS arm64 and Linux aarch64/x86_64,
so no compiler is needed in the dev venv or in the Colima containers. This follows the Phase 0 rule of
not adopting brand-new releases on the critical path (as with TypeScript 7 and mypy 2). Move to 0.32.x
once it has a few weeks of soak; record the bump in this ADR.

## Consequences

**asyncpg is async-only — there is no synchronous database access anywhere.**

| Former synchronous use | Now |
|---|---|
| Integration tests inspected the schema through a sync `Engine` | `SyncDb` helper (`tests/integration/conftest.py`): each call runs `asyncio.run` on a short-lived async engine and hands the code a sync-facing connection via `run_sync`. Migration tests stay **synchronous on purpose**: they call Alembic commands, and the async `env.py` runs its own `asyncio.run`, which would fail inside an already-running loop. |
| Test-database reachability probe used a sync engine | async engine + `asyncio.run` (collection runs outside any loop) |
| `doctor.py` connected with `psycopg.connect` | SQLAlchemy async engine with the app's exact `KEN_DATABASE_URL`, so host/port/query resolution matches the app and the guard |
| `Settings.sync_database_url` | removed — meaningless for an async-only driver, and unused |

**The port-5432 safety guard was preserved and re-verified.** It resolves the driver's *actual*
connection target through SQLAlchemy's asyncpg dialect (`create_connect_args`), so query-string
overrides cannot hide the port or host. Porting surfaced one real difference: **asyncpg returns
lists** for a libpq multi-host URL (`?host=a:5433&host=localhost:5432`) where psycopg returned
comma-separated strings. Treated as a string, a list would have produced fragments like `"['a'"` and
let `localhost:5432` in the second slot slip through. The guard now normalises both shapes, and a test
covers that exact case. Verified through the real Alembic CLI: every route to the developer's own
PostgreSQL is refused; `postgres:5432` (the compose service) and `localhost:5433` are allowed.

**Verified after the change:** Alembic `upgrade head → downgrade base → upgrade head` on
`ken_interlink_test` (table present → absent → present; only `plpgsql` ever installed), the full
integration suite, the API and worker against the project database, and the container images.

## Licence inventory after the change

Verified from installed package metadata. **There are no GPL or LGPL packages in the Python tree.**

| Package | Licence | Scope | Note |
|---|---|---|---|
| `asyncpg` | Apache-2.0 | runtime | this decision; no transitive dependencies |
| `certifi` | MPL-2.0 | runtime | CA bundle, via `httpx`. File-level copyleft: distributing it **unmodified** alongside proprietary code is permitted; keep its notice. |
| `pathspec` | MPL-2.0 | dev only | via `mypy`; never shipped |
| `sharp`, `@img/sharp-*` | LGPL-3.0-or-later | frontend build only | via `next`; **excluded from the runtime web image** (`images.unoptimized` + output-trace exclusion). **An Electron packager must re-verify this exclusion** — desktop bundlers copy `node_modules` differently from Next's standalone trace. |
| `lightningcss`, `axe-core` | MPL-2.0 | frontend build/dev | via Tailwind/Vite and `eslint-plugin-jsx-a11y`; not in any runtime bundle |

Everything else is MIT, BSD, ISC, Apache-2.0 or similarly permissive.

## Alternatives considered

- **Keep psycopg 3 (LGPL).** Fine for self-hosting, but rejected by the user because of possible
  desktop distribution.
- **asyncpg for the app + a second, sync driver for Alembic.** Unnecessary: `env.py` is already async.
  A second driver would mean two URL schemes and two places for configuration errors — the problem the
  single-driver rule exists to prevent. psycopg2 is also LGPL.

## History — original Phase 0 decision (superseded)

Phase 0 adopted `psycopg[binary,pool]==3.3.6` as the single driver, sync and async through
`postgresql+psycopg://`, because one package served both modes. Its LGPL-3.0-only licence was
recorded here and flagged for user confirmation; the independent QA review later found that
`psycopg-pool` also carried that licence. The user resolved the flag by choosing asyncpg (above).
