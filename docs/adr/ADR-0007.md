# ADR-0007 — Hybrid local development topology

- **Status:** Accepted (user decision, 2026-10-13)
- **Phase:** 0

## Decision

**Mode A — the preferred, default development loop:**

| Component | Where | Address |
|---|---|---|
| PostgreSQL | container (`pgvector/pgvector:pg16`) | `127.0.0.1:5433` |
| Ollama | the developer's **existing host daemon** | `127.0.0.1:11434` |
| FastAPI | native process | `127.0.0.1:8000` |
| Next.js | native process | `127.0.0.1:3000` |

Because FastAPI runs natively, it reaches the host Ollama directly. **Normal development never requires
exposing Ollama on `0.0.0.0`**, and never involves `host.docker.internal`.

**Mode B — optional full-container stack** (`docker compose --profile full up -d --build`) adds
`migrate`, `api`, `worker` and `web`. It defaults to `KEN_MODEL_PROVIDER=mock`, so it is fully
functional without any model server.

**The compose `ollama` service is opt-in only** (`--profile ollama-container`). It publishes no host port
(11434 belongs to the host daemon) and pulls no model.

## Why

- The host daemon already exists, already has `qwen3:8b-q4_K_M`, and has Metal/GPU acceleration. A
  macOS container has none and is roughly an order of magnitude slower.
- A containerised API cannot reach a `127.0.0.1`-bound host daemon. Making it reach would mean
  exposing Ollama to the network — an unnecessary security trade-off for local development.
- `docker-compose.override.yml.example` documents that trade-off for anyone who chooses it. It is
  explicitly optional.

## Consequences

- `KEN_REQUIRE_OLLAMA=false` in both modes, so an absent model server degrades `/ready` (HTTP 200)
  rather than failing it.
- TRD §21's five services all exist in `docker-compose.yml`, satisfying the spec, while the daily loop
  stays fast.
