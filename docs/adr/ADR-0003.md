# ADR-0003 — pgvector is provisioned, not enabled, in Phase 0

- **Status:** Amended by [ADR-0010](ADR-0010-content-intelligence.md) (2026-10-14): migration 0003 enables pgvector. Accepted (revised per explicit user decision)
- **Date:** 2026-10-13
- **Phase:** 0

## Context

TRD.md names PostgreSQL + pgvector as the initial system of record and vector layer, and Phase 0's
deliverables include "pgvector readiness".

The developer's machine runs Homebrew PostgreSQL 16 on port 5432, which also hosts an unrelated
`automation_dashboard` database. It has **no** pgvector: `pg_available_extensions` returns zero rows
for `vector`. Installing it is not simple: the Homebrew `pgvector` 0.8.7 formula declares build
dependencies on `postgresql@17` and `postgresql@18` only and installs into their directories, so
`brew install pgvector` would **not** make `CREATE EXTENSION vector` work on PG 16. (Verified against
the live formula source.)

## Decision

1. **The project database runs in a container**, `pgvector/pgvector:pg16`, published on host port
   **5433** → container 5432. The developer's own PG 16 on 5432 is never touched.
2. **Migration 0001 creates the `events` table only.** It runs no `CREATE EXTENSION` and creates no
   vector column.
3. **`CREATE EXTENSION IF NOT EXISTS vector` is deferred to Phase 2**, into the same migration that
   creates the first `vector` column (on `page_embeddings`). Enabling an extension in the migration
   that needs it keeps schema state and revision id in lockstep.
4. **Readiness reports availability without depending on it.** The `pgvector` probe reads
   `pg_available_extensions` and `pg_extension`. It is optional unless `KEN_REQUIRE_PGVECTOR=true`.
5. **Native degraded mode is supported.** With `KEN_REQUIRE_PGVECTOR=false` (the default),
   migrations succeed, the API starts, and `/ready` returns 200 `degraded` against a PG 16 with no
   vector extension at all.

## Why not create the extension in 0001

A migration that cannot execute against the only natively-available database turns
`alembic upgrade head` from a green gate into a permanently red one. The predictable "fix" is a
`try/except` around the DDL — which is exactly the *"disabling validation merely to make a build
pass"* that AUTONOMY_AND_PERMISSIONS.md lists under BLOCK. Env-conditional DDL is worse still:
schema state silently diverges from the revision id.

Phase 0 therefore satisfies "PostgreSQL + pgvector" through **provisioning and observability**,
not DDL.

## Guardrail

Three layers protect this decision. Be precise about which ones run automatically:

| Layer | Runs automatically? |
|---|---|
| Static test `test_migration_0001_never_enables_extensions_or_vectors` (scans the migration source) | **Yes** — part of `make verify` and every `pytest` run |
| CI job `native-degraded-mode` (round-trip on plain `postgres:16`, no pgvector) | Authored, but **has never run**: the repository has no git remote |
| Manual round-trip on a throwaway vector-less Homebrew PG 16 cluster | **No** — run once on 2026-10-13 (upgrade → downgrade → upgrade, plus the API returning 200 `degraded` / 503 under each `KEN_REQUIRE_PGVECTOR` value); evidence in PHASE_0_REPORT.md |

So today the automatic guard is the static test. The executable round-trip becomes a standing
regression test once CI runs.

## Consequences

- Phase 2 must add `CREATE EXTENSION IF NOT EXISTS vector` in its first vector migration, and read
  the embedding dimension from `ModelProvider.capabilities().embedding_dimensions` rather than
  hardcoding it.
- Developers who want vector support natively must run PostgreSQL 17/18 with the Homebrew bottle,
  build pgvector from source against PG 16, or use the container. Phase 0 requires none of these.
