# Claude Code Operating Instructions — Ken Interlink OS

You are working inside the Ken Research Agentic Interlinking OS repository.

## Mandatory First Step

Before editing code, read START_HERE.md, PRD.md, TRD.md, AUTONOMY_AND_PERMISSIONS.md, REPO_CLONE_PLAN.md and IMPLEMENTATION_PLAN.md.

Treat these files as the governing project specification.

## Non-Negotiable Constraints

1. Do not introduce mandatory paid APIs.
2. Default to local/self-hosted inference.
3. Do not add OpenAI, Anthropic, Gemini, paid Browser Use Cloud, managed vector databases or paid SaaS dependencies unless the user explicitly changes project constraints.
4. PostgreSQL is the primary system of record.
5. pgvector is the initial vector layer.
6. Ollama is the initial model server.
7. LangGraph is the initial supervisor/state-machine framework.
8. Prefer deterministic code over LLM reasoning whenever possible.
9. Every LLM output that crosses a service boundary must be validated with Pydantic.
10. No LLM may write directly to production storage.
11. All production content changes must pass through a controlled CMS adapter/API.
12. Every mutation must be idempotent, version-aware, auditable and reversible.
13. Every DB schema change requires an Alembic migration.
14. Every new endpoint requires tests.
15. Every material agent capability requires evaluation fixtures.
16. Agents may propose policies/skills but may not self-promote them.
17. Do not silently modify architecture decisions. Create an ADR or ask the user.
18. Do not clone reference repositories into application source folders.
19. Never copy code from a reference repository without checking its license and documenting provenance.
20. Do not persist secrets in source control.

## Default Autonomous Permissions

You MAY proceed without asking for permission to inspect repository files, create local source files, create tests, refactor within approved architecture, run local tests, run linters/type checkers, run formatting, create local Docker/dev configuration, create Alembic migrations, create documentation, use mock data, add dependencies already approved in TRD.md, and read reference repositories under `_research/repos/`.

## You MUST Ask Before

- deleting/replacing a large set of files;
- force-resetting or rewriting Git history;
- publishing/pushing to remote Git;
- creating or merging a pull request;
- touching production CMS data;
- using real CMS write credentials;
- running destructive database commands;
- enabling AUTO_APPROVE;
- promoting a learned skill or policy to production;
- materially changing the approved architecture stack;
- introducing a new infrastructure service;
- adding a dependency with restrictive/unclear licensing;
- calling any paid external API;
- sending repository data to an external service;
- executing arbitrary shell commands generated by an LLM;
- changing secrets/authentication settings;
- deploying to a live environment.

## When Permission Is Needed

Explain what action you want to take, why, exact scope, risks and rollback path. Then wait for explicit approval.

## Development Discipline

Work one implementation phase at a time.

At the end of every phase:
- run tests;
- run lint/type checks;
- summarize files changed;
- summarize architecture impact;
- document known limitations;
- update NEXT_STEPS.md;
- stop before the next phase unless explicitly instructed otherwise.

## Agent Design Rule

Agents receive tools, not raw infrastructure credentials. Tools must be narrow, typed, allowlisted, logged and permission-aware.

## Model Design Rule

Do not hardcode a specific model into business logic. Use MODEL_FAST, MODEL_REASONING and MODEL_EMBEDDING through a provider abstraction.

## Learning Design Rule

Never implement uncontrolled self-modification.

Learning pipeline:
experience → structured feedback → proposal → offline eval → shadow/canary → explicit promotion
